# SPEC Command Capture

These scripts capture SPEC CPU reference workload commands from fake harness runs and replay them. They work with both SPEC CPU2017 and SPEC CPU2026: the two releases emit the same `runcpu --fake` command markers (`Running Benchmarks`, `%% Fake commands from benchmark_run`/`compare_run`, per-benchmark `cd`), and the scripts never assume a particular benchmark set -- they parse whatever benchmarks the fake log contains. A manifest captures three kinds of commands: benchmark invocations (`commands`), post-processing invocations that convert raw benchmark output into the comparable form (`pre_compare_commands`), and the compare/specdiff invocations used to verify that output (`verify_commands`). It does not capture build commands, PGO training commands, or input-generation commands.

`generate_command_file.py` writes JSON manifests only. Shell command files are not generated by the current workflow.

No manifest is shipped with the repository -- `*.json` is git-ignored, so you always generate one with `generate_command_file.py`. All three scripts default to the same file name, `commands.json`: `generate_command_file.py` writes `./commands.json` (relative to the current directory), while `run_spec_with_wrapper.py` and `verify_runs.py` read `commands.json` from next to the scripts -- the same file when you run the generator from this directory. It does not exist until you generate it, so run the generator first, or pass `--commands-file`/`--output` to use another path. Generate a manifest per install/config rather than reusing one across machines.

## End-to-End Example

Generate a config-specific command file, building binaries and setting up run directories first:

```bash
./generate_command_file.py \
  --config myconf.cfg \
  --build-ncpus 96 \
  --output commands.json
```

The generator defaults to `--install-root ../`, which is convenient when run from this command-capture directory. Pass `--install-root /path/to/spec-install` if you run it from somewhere else.

Run the generated commands through a wrapper such as Intel Pin, using conservative per-benchmark scheduling:

```bash
./run_spec_with_wrapper.py \
  --install-root ../ \
  --commands-file commands.json \
  --jobs -1 \
  --serialize-benchmark-commands \
  -- /path/to/pin -t /path/to/custom-tool -- {benchmark_cmd}
```

`{benchmark_cmd}` expands to the benchmark executable, arguments, and parsed file redirects from the generated JSON.

## Top-Level Structure

```json
{
  "generated_from": ["./..."],
  "setup_required": ["..."],
  "commands": [{ "...": "..." }],
  "pre_compare_commands": [{ "...": "..." }],
  "verify_commands": [{ "...": "..." }]
}
```

- `generated_from`: source fake-run logs used to produce the manifest.
- `setup_required`: `runcpu --action=setup` commands that must be run before replaying the manifest. This materializes run-directory executable links and generated inputs such as `BuckBunny.yuv`.
- `commands`: ordered list of benchmark commands to run.
- `pre_compare_commands`: ordered list of post-processing commands that some benchmarks (`vpr`, `gem5`, `marian`, and several SPECspeed benchmarks) run between the benchmark and the compare, to turn raw output into the file the compare reads. Same entry format as `commands` but with `phase` set to `pre_compare`. Empty for benchmarks that need no post-processing; may be absent in older manifests. These are output post-processing, not benchmark work, so they should be run un-wrapped (`verify_runs.py` runs them; `run_spec_with_wrapper.py` does not).
- `verify_commands`: ordered list of compare/specdiff commands that check benchmark output, in the same entry format as `commands` but with `phase` set to `verify`. May be absent or empty in older manifests.

## Command Entries

Each object in `commands` has this structure:

```json
{
  "suite": "intrate",
  "benchmark": "500.perlbench_r",
  "phase": "benchmark",
  "command_index": 1,
  "cwd": "./install-root-relative/run/directory",
  "command": "./install-root-relative/executable ... > ./install-root-relative/output 2>> ./install-root-relative/error",
  "argv": ["./install-root-relative/executable", "arg1", "arg2"],
  "redirects": {
    "stdout": "./install-root-relative/output",
    "stderr-append": "./install-root-relative/error"
  }
}
```

- `suite`: SPEC suite, currently `intspeed`, `intrate`, `fpspeed`, or `fprate`.
- `benchmark`: SPEC benchmark name, such as `525.x264_r`.
- `phase`: command phase. Entries in `commands` use `benchmark`; entries in `pre_compare_commands` use `pre_compare`; entries in `verify_commands` use `verify`.
- `command_index`: one-based order of the command within that benchmark.
- `cwd`: working directory that the SPEC harness uses for this invocation.
- `command`: shell command string with normalized install-root-relative paths and shell redirections.
- `argv`: executable argument vector only. This excludes shell redirections.
- `redirects`: parsed shell redirections captured separately from `argv`.

Redirect keys use explicit stream/action names:

- `stdin`: read stdin from file, equivalent to `<`.
- `stdout`: write stdout to file, equivalent to `>` or `1>`.
- `stdout-append`: append stdout to file, equivalent to `>>` or `1>>`.
- `stderr`: write stderr to file, equivalent to `2>`.
- `stderr-append`: append stderr to file, equivalent to `2>>`.

## Path Normalization

The manifest normalizes executable paths and file-like command-line arguments to paths relative to the SPEC install root. Redirection targets are also install-root-relative paths.

This matches the SPEC harness command layout after `runcpu --action=setup` has been run. The setup step creates the run-directory executable links and performs benchmark-specific setup such as `x264` input generation.

Consumers should resolve `cwd`, file-like `argv` entries, and redirect target values against the install root before executing commands from another working directory. The `command` field can be run directly by a shell from the install root.

## Execution Order

The `commands` array is ordered exactly as the SPEC harness emitted the benchmark invocations. Consumers should execute entries in this order unless they deliberately implement SPEC-compatible scheduling.

Some benchmarks have multiple inputs or dependent stages. Most multi-command benchmarks use independent inputs, but some commands depend on files created by earlier commands. The known command-order-sensitive cases are `525.x264_r` and `625.x264_s`, where later stages depend on files produced by earlier stages.

Examples of multi-command benchmarks include:

- `500.perlbench_r` / `600.perlbench_s`: separate Perl workloads.
- `502.gcc_r` / `602.gcc_s`: separate compiler input/option combinations.
- `525.x264_r` / `625.x264_s`: pass 1, pass 2, then seek/dumpyuv stage; later stages depend on files produced by earlier stages.
- `557.xz_r` / `657.xz_s`: separate compressed inputs.
- `603.bwaves_s`: separate FP input streams.
- `503.bwaves_r`: separate FP rate input streams.

Some benchmarks also require setup-generated inputs. For example, `525.x264_r` and `625.x264_s` require `BuckBunny.yuv`, and `549.fotonik3d_r` / `649.fotonik3d_s` require generated `.dat` inputs. These are produced by the required `runcpu --action=setup` step, not by entries in `commands`.

## Replaying Commands

To replay a command from JSON:

1. Run the listed `setup_required` commands first if the run directories have not already been set up.
2. Run `commands` in manifest order.
3. For each entry, resolve `cwd` against the install root and change to that directory.
4. Execute `argv` as the process argument vector.
5. Apply each `redirects` entry as the equivalent shell redirection.

The `command` field can be used directly by a shell from the install root if preferred, but `argv` plus `redirects` is safer for programmatic runners.

## Wrapper Runner

`run_spec_with_wrapper.py` runs the captured benchmark commands through a user-provided wrapper command. It resolves the benchmark executable and redirect targets to absolute paths, reconstructs each benchmark command from `argv` plus `redirects`, and executes each wrapper invocation in a subshell rooted at the captured benchmark working directory. Non-executable argv paths that point inside the captured working directory are rendered relative to that directory to preserve benchmarks that treat an argument as a name or input stem.

Example conservative Intel Pin-style usage:

```bash
./run_spec_with_wrapper.py \
  --install-root /path/to/spec-install \
  --commands-file commands.json \
  --jobs 8 \
  --serialize-benchmark-commands \
  -- /path/to/pin -t /path/to/custom-tool -- {benchmark_cmd}
```

`--commands-file` is optional. If omitted, it defaults to `commands.json` next to `run_spec_with_wrapper.py`.

Each command is rendered as:

```bash
( cd <resolved-cwd> && <wrapper with substitutions> )
```

The main wrapper placeholder is `{benchmark_cmd}`. It expands to the full shell-quoted benchmark executable, arguments, and file redirects.

Other command placeholders are:

- `{benchmark_argv}`: benchmark executable plus arguments, without redirects.
- `{benchmark_args}`: benchmark arguments only, without executable or redirects.
- `{benchmark_command}`: alias for `{benchmark_argv}`.

Scalar placeholders are:

- `{install_root}`
- `{suite}`
- `{benchmark}`
- `{benchmark_name}`
- `{phase}`
- `{command_idx}`
- `{command_index}`
- `{cwd}`
- `{benchmark_cwd}`
- `{benchmark_exe}`
- `{stdin}`
- `{stdout}`
- `{stdout_append}` or `{stdout-append}`
- `{stderr}`
- `{stderr_append}` or `{stderr-append}`

Missing redirect placeholders (`{stdin}`, `{stdout}`, `{stdout_append}`, `{stdout-append}`, `{stderr}`, `{stderr_append}`, `{stderr-append}`) expand to `/dev/null`.

Command placeholders must be standalone wrapper arguments because they expand to shell command fragments. Scalar placeholders may be embedded inside larger wrapper arguments, such as `--name={benchmark_name}`.

Use `--placeholder NAME COMMAND` to define a custom scalar placeholder. The runner renders built-in scalar placeholders in `COMMAND`, runs it once per benchmark command from `--install-root`, captures stdout with trailing newlines removed, and exposes the result as `{NAME}` in the wrapper. The command is evaluated even for `--dry-run` so the printed wrapper command is fully rendered.

Example:

```bash
./run_spec_with_wrapper.py \
  --install-root /path/to/spec-install \
  --commands-file commands.json \
  --placeholder simpoints_file 'python3 /path/to/get_simpoints_path.py {benchmark_name} {command_index}' \
  -- /path/to/pin -t /path/to/custom-tool -simpoint_file {simpoints_file} -- {benchmark_cmd}
```

`--jobs N` runs rendered commands in parallel. The default is `--jobs 1`, so commands run in manifest order unless parallelism is requested. `--jobs -1` uses one worker per rendered command after filtering.

The runner attempts every rendered command even if earlier commands fail. It exits with the first nonzero command status if any command failed.

By default, commands for the same `(suite, benchmark)` pair are not grouped. With `--jobs > 1`, command indices from one benchmark may run concurrently. Use `--serialize-benchmark-commands` for conservative scheduling: each `(suite, benchmark)` pair becomes one work item, and its commands run sequentially in manifest order. With that flag, `--jobs -1` uses one worker per benchmark group.

`--benchmark` filters use case-insensitive substring matching against the full benchmark name. For example, both `--benchmark x264` and `--benchmark 525` match `525.x264_r`. `--skip-benchmark` uses the same matching rules to exclude benchmarks after the include filter is applied.

The runner does not run `setup_required` commands. Run those first if the run directories have not already been materialized.

## Verifying Outputs

`verify_runs.py` compares generated benchmark outputs without rebuilding or rerunning benchmarks. It defaults to `--commands-file commands.json` (the name `generate_command_file.py` writes), which is not shipped, so generate it first or point at your manifest:

```bash
./verify_runs.py \
  --install-root ../ \
  --commands-file commands.json
```

It chooses one of two strategies based on the manifest:

- If the manifest has a non-empty `verify_commands` list, it first replays any `pre_compare_commands` (post-processing), then replays each captured compare/specdiff command directly, in `( cd <run-directory> && ... )` form.
- Otherwise it falls back to finding each unique run directory and running that directory's `pre-compare.cmd` (when present) and then `compare.cmd` through `specinvoke`.

Benchmarks with a post-processing step (`vpr`, `gem5`, `marian`, and several SPECspeed benchmarks) fail verification without this: the compare reads a file that only the post-processing step produces.

Both paths require an initialized SPEC environment. Source the install's `shrc` first (or otherwise export `SPEC=<install root>` and put `bin` on `PATH`): the `verify_commands` path runs `specdiff`, which locates `compare.pl` via `$SPEC/bin/harness`, and the fallback path needs `specinvoke` on `PATH`. Without `$SPEC` set, `specdiff` fails with `Can't locate compare.pl in @INC`.

The script supports the same benchmark include/exclude filters as `run_spec_with_wrapper.py`:

```bash
./verify_runs.py --benchmark x264
./verify_runs.py --skip-benchmark nab
```

## Generating Commands

`generate_command_file.py` regenerates the concrete command manifest for a specific SPEC config. It runs the selected suites through SPEC clobber, build, setup, and fake run phases, parses the fake benchmark invocations into `commands`, the fake post-processing invocations into `pre_compare_commands`, and the fake compare invocations into `verify_commands`, and writes the same JSON schema consumed by `run_spec_with_wrapper.py` and `verify_runs.py`.

Provided configs (CPU2017):

- `gcc-pgo-lto-all.cfg`: static GCC PGO+LTO build with BOLT-friendly relocation and symbol retention.
- `gcc-pgo-lto-all-nopie.cfg`: same as above, plus compile-time `-fno-pic -fno-pie` and link-time `-no-pie` for more statically resolved binaries.

Provided configs (CPU2026):

- `gcc-pgo-lto-all-2026.cfg`: CPU2026 port of `gcc-pgo-lto-all.cfg` -- same PGO+LTO+static+BOLT recipe, with language standards raised to `c18`/`c++17`/`f2018` (CPU2026's C++ benchmarks do not build under `c++03`) and the benchmark portability sections replaced with the CPU2026 set from `$SPEC/config/Example-gcc-linux-x86.cfg`.
- `gcc-pgo-lto-all-nopie-2026.cfg`: CPU2026 port of `gcc-pgo-lto-all-nopie.cfg`, with the same standard/portability updates.

Example full-suite generation:

```bash
./generate_command_file.py \
  --config myconf.cfg \
  --build-ncpus 96 \
  --output commands.json
```

By default it includes `intspeed`, `intrate`, `fpspeed`, and `fprate`. Use repeated `--suite` flags to limit generation:

```bash
./generate_command_file.py \
  --config myconf.cfg \
  --suite intspeed \
  --suite intrate
```

The generator runs commands equivalent to:

```bash
./bin/runcpu --config=myconf.cfg --action=clobber --size=ref --tune=peak <suite>
./bin/runcpu --config=myconf.cfg --action=build --rebuild --size=ref --tune=peak --define build_ncpus=96 <suite>
./bin/runcpu --config=myconf.cfg --action=setup --size=ref --tune=peak --nobuild <suite>
./bin/runcpu --config=myconf.cfg --action=run --size=ref --tune=peak --iterations=1 --fake --nobuild <suite>
```

Useful options:

- `--install-root PATH`: SPEC install root. Defaults to `../`; relative paths are resolved from the current directory.
- `--build-ncpus N`: passes `--define build_ncpus=N` to the build phase. If omitted, this defaults to the machine CPU count reported by Python's `os.cpu_count()`.
- `--skip-build`: skip both clobber and build, reusing existing binaries.
- `--skip-setup`: reuse existing run directories.
- `--suite-config SUITE=CONFIG`: override `--config` for one suite.
- `--fake-log SUITE=PATH`: parse an existing fake-run log instead of running `runcpu --fake` for that suite.
- `--keep-going`: continue with later suites after a `runcpu` failure instead of aborting.
- `--output PATH`: choose the generated JSON path. Defaults to `./commands.json` relative to the current directory.
- `--log-dir PATH`: choose where generated fake-run logs are stored. Defaults to the current directory.

The output intentionally contains concrete run-directory paths and executable names for the config that generated it. To move across machines or use a different config label, regenerate this JSON on the target install/config rather than editing the manifest by hand.

## Development

The three scripts share path resolution, redirect handling, manifest loading, and command filtering through `spec_commands.py`. Path resolution is asymmetric on purpose: the executable, working directory, and redirect targets are absolutized, while benchmark arguments that point inside the run directory stay relative to it (some benchmarks echo an argument into their compared output or use it as a name/stem, so an absolute path would break verification). `test_spec_commands.py` locks in that behavior:

```bash
python3 -m unittest test_spec_commands
```
